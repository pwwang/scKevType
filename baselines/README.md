# Standard baselines on the real-v2 corpus

What a reviewer means by "compared to nothing" is a baseline they already trust, run on the
same cells, the same labels and the same questions as our model. This directory is that:
two standard annotators, plus one baseline built to match our model's task shape exactly.

**The asymmetry, stated once and repeated wherever a number appears.** Our model reads a
cell's **rank list** — `state` in the corpus, ~201 gene symbols with their ranks and *no
expression values* — plus the definitions of the candidate types it is asked about
(`docs/factory.md` lines 70-99 define the six families). Every baseline in steps 3, 4 and 6
is given the corpus's own cells, the corpus's own labels and the corpus's own option lists.
Steps 3 and 4 additionally see the **full expression matrix (all genes)** — strictly more
input than our model gets. Step 6 deliberately throws that advantage away and reproduces our
model's input instead, so that the only remaining difference is the model.

## What was run

| # | baseline | script | input | trained on |
|---|---|---|---|---|
| 3 | CellTypist (pretrained linear models) | `step3_celltypist.py` | full matrix, CP10K + log1p | nothing — pretrained; one arm per applicable model |
| 4 | logistic regression on HVGs | `step4_lr.py` | full matrix, 2,000 HVGs | arm `splitexact`: the corpus's own train split (hao_cite); arm `atlas`: every in-register hao_cite cell (133,541); arm `cv_indomain`: 5-fold CV inside the test dataset (reference only, not a transfer baseline) |
| 6 | logistic regression on the corpus's own task shape | `step6_panel_lr.py` | **rank list + option definitions only** — no expression values | the corpus's own train split records, one row per (record, option) pair |

Scoring (`step5_score.py`) is shared: one prediction per cell, per dataset, per family.

### Row order: the invariant every number in here depends on

These baselines label **matrix row i** with the label of `_cells.npy[i]`, so exactly one thing
has to be true of an extracted matrix: the id at row `i` is the cell whose expression is row
`i`. It was not, for a while. `step2_expr.extract` assembled rows in **ascending source-row
order** (what makes the reader fast — contiguous runs) while saving the cell ids in **request
order**, so almost every position named the wrong cell: measured, 1,979 of muraro's 2,126 ids,
3,499 of tabula_muris_senis's 3,500, 4,998 of siletti's 5,000 and all 1,841 hao_cite training
ids. Every positional consumer — step 3, step 4, the sweep — therefore attached its labels to
the wrong cells, and the affected numbers were **artifacts, not measurements**: muraro's
in-domain LR CV read 0.3085 against a 0.4283 majority floor, which looked like a finding about
the data and was purely the permutation.

Three things now hold, and each is checked rather than asserted:

* **The writer cannot produce it again.** `step2_expr.extract` saves the ids sorted by their
  own source position, both readers *refuse* a non-ascending row array instead of silently
  sorting it (`assert_ascending_rows`), and every extraction re-reads a spread of the persisted
  rows straight from the atlas, by content, at the source row each id names
  (`verify_alignment`) — a mismatch aborts the run instead of leaving a matrix behind.
* **The artifact carries its own proof.** Each `(dataset, split)` writes
  `<name>_order.json`: the digest of the exact id sequence on disk, the source-row positions,
  the sampled (row, source_row, cell_id) triples, and who verified it. `load_aligned_cells`
  refuses any array whose digest does not match, so a rewrite that forgets to re-certify fails
  loudly at the next consumer.
* **A stale arm cannot be scored.** `step5_score.py` compares every arm's own cell list with
  the certified row order before scoring it, so an npz written before the repair raises instead
  of producing a plausible number.

`audit_alignment.py` re-derives all of this from the atlases on demand (it does not read the
certificates): ascending-row order, `obs[position i] == id[i]`, and content re-reads. It exits
non-zero if any matrix is not in certified row order.

## How to read the numbers

Each family asks a different question, so each has its own decisive metric. Pooling them
would hide all of it.

| metric | what it is |
|---|---|
| `top-1 exact` | the arm's own best label equals the cell's register label (cell level) |
| `hierarchy-consistent` | …or one is an ancestor/descendant of the other in the CL snapshot (`artifacts/v2/cl_terms.json`) |
| `panel-restricted correct` | the arm's **argmax over that record's own option list** equals the record's target. This is the shape our model answers, so it is the number to compare against ours. An arm with no probability mass on any option is counted as *no signal*, not as a choice. |
| `answered` | share of cells where the arm had mass on at least one option |
| `no signal` | share of cells where the arm's class space contains none of the record's options |
| `balanced accuracy` (marker_noul) | mean of recall on the yes-cells and recall on the no-cells. Plain accuracy on this family is mostly the negative-class prior, so it is reported next to `always_no_accuracy`. |
| `named a register type anyway` (out_of_register) | share of cells whose own label is *not* a CL term for which the arm still named a register type. Nothing can be correct here; the informative number is how often the arm answers anyway. |
| `always_abstain_accuracy` (step 6) | the floor on families whose target is the abstain option: what a rule that always answers "other" scores |
| `type-only accuracy` (step 6) | the same fitted model's argmax with the abstain option **removed from the ballot** — how often it names the right offered type when it is not allowed to abstain. Read it beside the headline `accuracy`, which has abstain on the ballot: on `panel_choice` (target always a type) the two are far apart (muraro 23.6% with the abstain option on the ballot vs 68.0% with it off), which is a fact about the model's abstain bias rather than about its type discrimination. On `marker_noul` it is not informative — that family asks about one candidate, so with abstain off the ballot the only available answer is that candidate |

Step 6 fits **one** model over the train split's records from every family at once, which is the
honest reading of "the same task shape": it sees no family label, exactly like our model. The
consequence is a mixture in its training targets — three families have the abstain option as
their target and three do not — and the fitted rule resolves that mixture by abstaining more than
the type evidence warrants. That is why the `type-only` column exists: it separates "cannot tell
the offered types apart" from "prefers to abstain", and the two numbers together are what a reader
needs to judge this arm.

## The two tags every arm carries

Two facts decide whether two numbers may be put side by side, and neither is visible in the
number itself. Every table below carries both, per row:

* **`training_regime` — `in-domain` or `transfer`.** In-domain means the arm was fitted on the
  atlas it is scored on, using that atlas's own labels; it is a *reference ceiling*, not a
  competitor, and no honest baseline is allowed to do it. Transfer means fitted on hao_cite and
  scored on atlases it has never seen — **which is what our model does**. Our model's published
  number is a transfer number; the in-domain arms are a different measurement, and placing them
  in the same column as ours would be the easiest way to lose a reviewer.
* **`input` — `full matrix` or `fixed panel`.** Full matrix means the arm may read the whole
  expression matrix (initialised on 2,000 HVGs, or CellTypist's own model vocabulary). Fixed
  panel means it reads only the corpus's marker panel — the rank list and the option
  definitions, no expression values at all.

**Every baseline arm in steps 3 and 4 reads the full expression matrix; our model reads a fixed
marker panel. That asymmetry favours the baselines, and it is stated next to their numbers
rather than in a footnote.** The one arm with both of our model's tags — transfer, fixed panel —
is step 6.

| arm | training_regime | input | what it is |
|---|---|---|---|
| `lr_splitexact` | transfer | full matrix | LR on 2,000 HVGs fitted on the corpus's hao_cite train split |
| `lr_atlas` | transfer | full matrix | the same, fitted on every in-scope hao_cite cell of the train tier (133,541 cells) |
| `lr_cv_indomain` | in-domain | full matrix | 5-fold CV over **cells** inside the scored atlas — reference ceiling; donor structure crosses folds |
| `lr_cv_grouped` | in-domain | full matrix | leave-one-donor-out CV inside the scored atlas — reference ceiling, and the in-domain number to quote |
| `celltypist_*` | transfer | full matrix | a pretrained CellTypist model, never fitted on any corpus cell |
| `panel_lr` (step 6) | transfer | fixed panel | the corpus's own task shape: rank list + option definitions, fitted on the train split, scored on unseen atlases |
| our model | transfer | fixed panel | trained on hao_cite, scored on four unseen atlases |

## Leakage: what was checked before quoting an in-domain number

The in-domain arms read as 0.97–0.99 on two atlases, which is exactly the kind of number that
turns out to be an artefact. Step 4 answers the three questions that would explain it, and
records the answers in `out/step4_lr_summary.json` under `leakage_checks` (tabled by
`make_tables.py`):

1. **Does any scored atlas contribute a cell to a fit?** No. The transfer arms fit on the
   hao_cite train tier only, and the disjointness is asserted by `(dataset_id, cell_id)` pairs
   — bare barcodes collide across atlases, so a barcode-level check would be worthless.
2. **Are the HVGs selected on the whole matrix, test cells included?** No. `select_hvg` is
   called inside each fold on that fold's training rows, and the resulting column list is used
   for both sides of the fold. This matters more than it sounds: an HVG list chosen over all
   cells is a supervised step on the test set.
3. **Do the folds group by donor?** The cell-stratified arm does not — cells from one donor sit
   on both sides of every fold, which is the classic way a few donors with many cells inflate a
   CV number. `cv_grouped` answers it properly with leave-one-donor-out folds, and the two
   numbers sit side by side in the floors table. On muraro they differ by 0.5 points (0.9800 →
   0.9752, four donors), so the donor structure is *not* what produced these numbers; on an
   atlas where they diverge, the grouped number is the one to quote.

### What is still thin, said out loud

* A class with fewer cells than there are folds cannot be represented in every training fold.
  **siletti: `CL:0000576` (monocyte) has 3 cells among the 3,000 register-labelled cells**, so
  sklearn's 5-fold split warns about it (`The least populated class in y has only 3 members`);
  siletti's other thin classes are `CL:0000623` (4) and `CL:0000084` (9).
  **tabula_muris_senis is thinner still: 56 classes among 2,000 cells, eight of them with ≤2
  cells** — two with 2 (`CL:0002063`, `CL:0002275`) and six with 1 (`CL:0000815`, `CL:0000784`,
  `CL:0000451`, `CL:0000097`, `CL:0002079`, `CL:0002543`). Their per-class accuracy is not a
  measurement, and the majority-class floor is what the aggregate numbers should be read
  against. Every CV block carries `classes_with_fewer_cells_than_folds` so this cannot be
  discovered only from a warning in a log.
* The transfer arms on muraro are **structurally unable**, not bad: an arm fitted on hao_cite's
  16 PBMC classes cannot emit any of muraro's 7 pancreas types, so its 0.0 is geometry (see
  `label_space_overlap`). This is why step 6 exists.

### Two ways a "0.0" can be uninformative

1. **Structurally unable.** An arm trained on hao_cite's classes (16 PBMC types: monocyte,
   naive T, NK …) cannot emit any of muraro's seven pancreas types (alpha, beta, ductal …).
   The label spaces are disjoint — verified in `results.json` under
   `inventory.label_space_overlap` — so its score on muraro is 0.0 *by construction*, not by
   measurement. Read those cells as "this classifier cannot attempt the question", and note
   that it is still asked, answers anyway, and is never right.
2. **Below the floor.** On a fine-grained dataset a model can score worse than the majority
   class. `inventory.floors` gives, per dataset, the majority-class rate and the
   prevalence-weighted chance rate for that dataset's register-labelled cells, so every
   accuracy above can be read against it. tabula_muris_senis has 56 true types among 2,000
   register-labelled cells, so its floor is much lower than muraro's 7-type floor.
